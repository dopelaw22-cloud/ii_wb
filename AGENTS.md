# Агенты «Менеджер WB»

## orchestrator
Точка входа. Маршрутизирует задачи на агентов, ведёт журнал в БД `wb_ops`.
Скрипты: `wb_api_check.py` — проверка доступа ко всем разделам WB API.

---

## 1. analyst — аналитик магазина

Считает юнит-экономику и прибыль по каждому товару, разбирает рекламу,
карточки и воронку продаж, выдаёт рекомендации. Отвечает владельцу в Telegram.

### Что отвечает на какой вопрос

| Вопрос владельца | Источник | Скрипт |
|---|---|---|
| Сколько я зарабатываю с единицы? | тарифы + себестоимость + цены | `unit_economics.py` |
| Сколько WB удержал на самом деле? | финотчёт реализации | `pull_finance.py` |
| Куда уходят деньги на рекламу? | статистика кампаний | `pull_adverts.py` |
| Где теряется покупатель? | воронка продаж | `pull_funnel.py` |
| Что не так с карточками? | контент-API | `pull_products.py` |
| Когда кончится товар? | остатки + темп продаж | `pull_stocks.py` |
| Что делать прямо сейчас? | все правила вместе | `analyze.py` |

### Два основания расчёта прибыли

**plan** — по тарифам. Цена из прайса, комиссия по предмету, логистика по
объёму, себестоимость из таблицы владельца. Доступен всегда. Отвечает:
«сколько *должно* оставаться».

**fact** — по финотчёту. Берутся реальные удержания WB: комиссия, логистика,
обратная логистика, хранение, приёмка, штрафы, эквайринг. Отвечает:
«сколько осталось *на самом деле*».

Расхождение между plan и fact — самостоятельная находка: значит WB удержал
больше, чем следует из тарифа.

Формула plan на одну проданную единицу:

```
  выручка        = цена со скидкой продавца
− комиссия       = выручка × кВВ%
− логистика      = тариф(объём) / доля_выкупа
                   + обратная логистика × (1/доля_выкупа − 1)
− хранение       = тариф_хранения(объём) × дней_оборачиваемости
− реклама        = затраты на рекламу / проданных единиц
− себестоимость
− налог
= прибыль
```

Логистика делится на долю выкупа потому, что WB берёт доставку за каждую
отправку, включая невыкупленные.

### Правило о неполных данных

Если не хватает тарифа, себестоимости или цены — прибыль остаётся **пустой**
(`NULL`), а не считается по нулям. Показать «маржа 80%» вместо прочерка хуже,
чем не показать ничего: на такую цифру принимают решения. Все пропуски
перечисляются в блоке «чего не хватает» и в `detail.missing`.

### Пороги рекомендаций

Заданы в `analyze.py`, словарь `TH` — менять там:

| Показатель | Порог |
|---|---|
| прибыль с единицы | ниже 0 → critical |
| маржа | ниже 15% → warn |
| ROI | ниже 30% → info |
| ДРР | выше 15% → warn, выше 30% → critical |
| затраты при нуле заказов | любые → critical |
| CTR | ниже 1% при 1000+ показов → warn |
| выкуп | ниже 85% → warn |
| конверсия в корзину | ниже 5% при 300+ переходах → warn |
| остатка хватит на | меньше 14 дней → warn, меньше 7 → critical |
| затоваривание | больше 90 дней → info |
| фото / характеристики | ниже уровня лучшей своей карточки → warn |

### Telegram-бот

Бот `@wb_permin_bot`, токен `WB_TG_BOT_TOKEN` в `.env`.
Служба: `systemctl --user {status,restart} wb-analyst-bot`
(нужен `export XDG_RUNTIME_DIR=/run/user/1001`).

Владелец привязывается по первому `/start`, его `chat_id` пишется в
`wb.setting.owner_chat_id`. Посторонним бот не отвечает.

Команды: `/сводка` `/прибыль` `/реклама` `/воронка` `/карточки` `/остатки`
`/советы` `/отчет` `/данные` `/лимиты` `/обновить` `/налог N`.

Свободный текст уходит в headless-сессию Claude с правами только на чтение
(`--permission-mode none --allowedTools "Bash(psql*)" Read Grep Glob`).
Переписка сохраняется в `wb.tg_message`.

### Таблицы в БД

Схема `wb` базы `wb_ops`: `product`, `cost`, `price`, `sale`, `order_row`,
`finance_row`, `funnel`, `advert`, `advert_stat`, `stock`, `tariff`,
`unit_econ`, `recommendation`, `setting`, `tg_message`.

Журнал прогонов — `ops.agent_run`, события — `ops.event_log`,
решения владельца — `ops.owner_decision` (туда пишется смена налога через бот).

### Чего агент не делает

Ничего не пишет в WB: не меняет цены, не правит карточки, не управляет
ставками, не отвечает на отзывы. Только читает и советует. Любая запись
в WB — отдельное решение владельца (железное правило проекта).
